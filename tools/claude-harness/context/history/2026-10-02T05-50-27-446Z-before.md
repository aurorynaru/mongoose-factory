# 1\. Project and workflow

The project is an autonomous **Infor Mongoose factory** being built in C:\\AI\\mongoose-factory. Its long-term goal is to take a natural-language request, optionally with reference images, and reliably build Mongoose Forms/portal-related artifacts using browser automation and a growing set of verified recipes.

There are three roles:

-   **Coordinator (ChatGPT):** decides the next bounded experiment step, reviews worker evidence, decides whether specialist consultation is needed, and controls knowledge promotion from candidate → observed → replay-verified.
-   **OpenCode worker:** operates the actual Mongoose browser through Playwright MCP, writes/updates experiment records, recipes, and evidence files, and must follow the current experiment scope exactly.
-   **Infor Mongoose specialist GPT:** provides Mongoose-domain guidance when a genuinely new concept or unexplained product behavior appears. Its advice is candidate guidance until the browser environment proves it.

The preferred learning pattern is:

```text
specialist guidance if needed
→ controlled EXP-N browser experiment
→ write observed recipe/procedure if successful
→ fresh OpenCode session
→ EXP-N-R2 clean replay
→ promote recipe/procedure to verified only if replay succeeds
```

The **observed → replay-verified** distinction is a factory/harness quality rule, not an Infor-defined validation level.

A replay stopped because one of its own required acceptance conditions cannot be satisfied is **blocked**, not evidence that the underlying procedure failed.

“Fresh worker context” or “independent execution” means independent at the harness/OpenCode-session level. It does **not** imply replication in a different Mongoose environment, configuration, user class, or product version.

The harness/controller automates this coordination. Future coordinator replies must respect the harness action protocol and experiment boundaries supplied by the controller.

Current Infor documentation supports that closing a Form can leave the Form and associated global Form objects in memory. Therefore ordinary close/reopen is not necessarily a complete Form/global-object cache boundary.

Unload All Global Form Objects is documented as clearing cached Form/global-Form-object information. With the relevant preference enabled, IDO metadata can also be cleared. “Global Form Objects” names a Mongoose object category; it must **not** be interpreted as proof of tenant-wide, server-wide, or all-user cache invalidation.

There remains a documentation ambiguity around Unload IDO Metadata With Forms: current development/cache documentation ties IDO metadata clearing to explicit global Form object unloading, while current Web Client Behavior documentation describes unloading IDO metadata **when Forms are closed**. EXP-006/R2 deliberately did not isolate those triggers. Therefore the exact **2026.09.08** trigger behavior—ordinary close, explicit unload, or both—remains **unverified**.

Current online product references used by the specialist are principally **2026.10/2026.x**, not an exact archived 2026.09.08 documentation set. Browser evidence remains authoritative for exact 2026.09.08 wording and observed behavior.

# 3\. Decisions and rules established so far

Permanent factory knowledge must be evidence-based:

```text
candidate guidance
→ observed
→ replay-verified
```

A recipe/procedure is verified only after a clean replay in a fresh OpenCode conversation reproduces its required semantic postconditions.

Core rules:

-   Modify only factory-owned FX\_ artifacts.
-   Never alter unrelated/non-FX\_ artifacts.
-   Never weaken security or expose credentials.
-   Keep experiments narrowly scoped to one new capability.
-   Read current state before retrying; never blindly replay a mutation after interruption.
-   Record failures, blockers and corrections, not just successes.
-   Evidence should prove state transitions, not every click.
-   A runtime screenshot proves only that a visual state rendered at that moment.
-   An independent Designer reopen is a practical UI-level persistence test, not direct proof of a durable Forms-database row.
-   A newly opened Designer tab is not automatically a complete cache boundary.
-   Explicitly distinguish editing permission from editing scope.
-   Identify the exact Form version by **Form name + ScopeType + ScopeName**.
-   Because multiple scoped Form versions can exist, never treat matching Form Name alone as proof that the intended version was reopened.
-   Treat specialist/documentation guidance as candidate evidence for exact 2026.09.08 behavior until browser evidence proves it.
-   Do not generalize beyond the environment, property/component types and workflow actually replayed.
-   Save semantics must be learned experimentally.
-   After editing Form metadata, compare the saved value with the same scoped Form version after the experiment's required cache/reopen boundary.
-   Do not invent undocumented APIs, direct DB changes, or metadata hacks.
-   In Select Form, explicitly select the intended row rather than assuming Enter activates the filtered row.
-   If an experiment defines a prerequisite, obey it even when the product itself might permit another path.
-   Do not change Unload IDO Metadata With Forms merely to satisfy an experiment unless separately approved.
-   Form/global-object cache and IDO metadata cache are distinct concepts, although a supported unload can clear both when the preference is enabled.
-   **Unload All Global Form Objects is cache invalidation, not persistence.** The Form change must already have been saved. The unload tests retrieval after the stronger tested cache boundary; it does not participate in Save.
-   Treat the unload as **broad Form/global-object cache invalidation within the exercised session/context**, with possible IDO-metadata clearing when the preference is enabled. Do not infer wider system scope without evidence.
-   EXP-005-R2 remains a historically **blocked replay**; later experiments do not retroactively change that result.
-   **EXP-006 + EXP-006-R2 replay-verify literal User-scope Form Caption persistence across the specific coupled unload used in these experiments.**
-   That verification is narrow: it does not verify other Form properties, localized/translatable Captions, Site/Group/Vendor scope, other unload mechanisms, cache internals, or other Mongoose versions.
-   Repeated Ext IDs, store indexes, model IDs, internal request paths and component structures are diagnostic observations, not durable recipe dependencies.
-   If existing evidence already proves an acceptance check, reuse it instead of performing redundant browser operations.
-   If Web Client list data and reopened Designer properties show different values, record only the observed difference unless the list/projection contract is known; do not infer stale data, fallback logic, cache defects, or persistence failure.

Current naming conventions:

```text
Forms:       FX_<Purpose>
Components:  FX_<SemanticPurpose><MongooseType>
Variables:   FX_<Purpose>Var   (candidate from EXP-004; no verified variable recipe)
```

# 4\. Lessons learned and pitfalls per experiment

**EXP-001 — Environment fingerprint**

Established browser architecture, User-scope behavior, version information, and basic Web Client / Web Designer navigation. Editing permission and editing scope are separate concepts.

**EXP-002 / EXP-002-R2 — Basic Form creation**

Verified recipes/forms/create-basic-form.md.

Reliable semantic path:

```text
Web Designer
→ New
→ New Form
→ Classic
→ BuildFromScratch
→ wizard
→ Save Template unchecked
→ Finish
```

Finish persisted the blank Form immediately, and R2 reproduced creation in a fresh worker context.

Pitfalls include wrong-row activation in Select Form, portal notifications intercepting clicks, drifting Ext IDs, and unreliable synthetic DOM events.

This verified recipe was subsequently reused in later Form-property experiments.

**EXP-003 / EXP-003-R2 — Component Fundamentals**

Verified:

-   recipes/components/add-component-from-toolbox.md
-   recipes/components/configure-basic-component.md

Verified component types:

-   Static
-   Edit
-   Button

Generated names, IDs, numeric type codes and internal event traffic are not supported selector/schema contracts. Recipes depend on semantic postconditions after reopen.

**EXP-005 — Form Caption Persistence**

Status: **COMPLETE — persisted postcondition observed, not independently replayed by EXP-005-R2.**

FX\_FormPropertyLab01 was created in User scope. Caption was the only Form property intentionally edited, to:

```text
Form Property Lab
```

Ordinary Designer Save returned clean. Closing/reopening the same User-scope Form showed the Caption again, and the recorded comparison properties were unchanged.

This experiment did not deliberately invalidate cached Form/global-object definitions.

Additional observations:

-   Runtime title reflected the Caption.
-   A long-lived Select Form dialog displayed data that differed from the subsequently observed Designer Caption; mechanism and projection semantics were unverified.
-   Web Client → Designer auto-loading the current Form was observed once.
-   Scope was literal Caption only, not localization/translatable Strings.

**EXP-005-R2 — Clean Replay: Literal Form Caption Persistence**

Status: **BLOCKED UNDER ITS OWN ACCEPTANCE CRITERIA.**

**EXP-006 — Literal Form Caption Persistence Across Documented Coupled Unload**

```text
Form Property Lab Coupled Unload
```

The recorded comparison properties remained unchanged.

After ordinary Save and close, Unload IDO Metadata With Forms was confirmed CHECKED and left unchanged. **Unload All Global Form Objects** was invoked exactly once. The same User-scope Form version reopened with the Caption present and all recorded comparison properties unchanged.

EXP-006 established the observed procedure that R2 subsequently replayed.

**EXP-006-R2 — Clean Replay: Literal Form Caption Persistence Across Documented Coupled Unload**

Status: **COMPLETE — replay\_verified; all acceptance checks passed.**

A fresh worker context proved FX\_FormPropertyLab04 absent, then created exactly one new User-scope BuildFromScratch Form using the verified creation recipe.

Baseline identity and comparison properties were captured. Caption was the only Form property intentionally edited, to:

```text
Form Property Lab Coupled Unload Replay
```

The experiment did not perform a complete binary/metadata diff of the whole Form definition; therefore it establishes intentional mutation scope plus unchanged recorded comparison properties, not that no incidental metadata anywhere changed.

Ordinary Save returned clean. The Form was closed. Unload IDO Metadata With Forms was independently confirmed **CHECKED/enabled** without mutation.

The exact command:

```text
Form
→ Definition
→ Unload All Global Form Objects
```

was invoked exactly once.

The exact same User-scope version—same Form Name, ScopeType=User and ScopeName—was reopened. The reopened Designer/effective Form definition showed the saved Caption. Description, Version, Device Type, Form Type, Is Master, ScopeType and ScopeName all matched baseline.

Final audit found exactly one FX\_FormPropertyLab04, nine FX\_ Forms among 640 Forms at that snapshot, the preference still checked with no unsaved mutation, and repository changes confined to the EXP-006-R2 record and evidence directory.

Therefore the procedure first observed in EXP-006 is now **replay-verified by two clean harness/worker-level executions in the same Mongoose environment/configuration lane**. This is not cross-environment replication.

A separate browser observation occurred during R2: Web Client GetAllForms/list data displayed a value equal to the Form Name while the reopened Designer showed the saved Caption. Whether this reflects display mode, projection semantics, fallback behavior, caching, or another mechanism is **unverified**. No GetAllForms contract establishing that this value must equal the Caption has been proven, and this observation does not affect the Caption-persistence result.

# 5\. Negative findings / blocked topics and why

**EXP-004 — Form Variable Fundamentals is blocked.**

Correct Form-variable UI:

```text
Web Designer
→ Details
→ Variables
```

Edit → Variable opens **Global Objects** and is not the Form-variable creation path.

FX\_TestValueVar could be created with:

```text
Global = False
Persistent = False
Value = Seed-A
```

Its definition then failed to survive:

-   ordinary Form Save: **2/2 failures**
-   Regenerate Form: **1/1 failure**
-   total: **3/3 failures**

No variable recipe exists.

This is anomalous relative to the documented model but does not prove a product defect. Possible causes remain a 2026.09.08 defect, configuration issue, scope/version interaction, an unobserved prerequisite, or other environment-specific behavior.

Persistent=False concerns persistence/lifetime of the variable's **value**; it does not explain disappearance of the variable definition.

Do not work around EXP-004 using bindings, scripts, undocumented APIs, DB edits, Global=True, Persistent=True, or manual metadata manipulation.

**EXP-005-R2 remains historically blocked by its own isolation criteria.**

EXP-006 and EXP-006-R2 establish a separate replay-verified procedure; they do not retroactively make EXP-005-R2 successful.

Important unresolved questions remain separate from that verified postcondition:

-   Why did Web Client GetAllForms/list data show a value equal to the Form Name while the reopened Designer showed the saved Caption? The projection/display contract and mechanism are **unverified**.
-   Whether similar persistence behavior applies to other Form-level properties, localization/translatable Strings, other Form scopes, other cache boundaries, other users/configurations, or other Mongoose versions is **unverified**.
-   The successful EXP-006/R2 pair establishes repeatability within the current harness/environment lane, not portability across environments.

The next learning experiment should target a **new small capability**, not repeat Caption persistence again, unless a later regression/revalidation need specifically justifies another replay.
