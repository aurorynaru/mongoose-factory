# 1. Project and workflow

The project is an autonomous **Infor Mongoose factory** being built in C:\\AI\\mongoose-factory. Its long-term goal is to take a natural-language request, optionally with reference images, and reliably build Mongoose Forms/portal-related artifacts using browser automation and a growing set of verified recipes.

There are three roles:

-   **Coordinator (ChatGPT):** decides the next bounded experiment step, reviews worker evidence, decides whether specialist consultation is needed, and controls knowledge promotion from candidate → observed → replay-verified.
-   **OpenCode worker:** operates the actual Mongoose browser through Playwright MCP, writes/updates experiment records, recipes, and evidence files, and must follow the current experiment scope exactly.
-   **Infor Mongoose specialist GPT:** provides Mongoose-domain guidance when a genuinely new concept or unexplained product behavior appears. Its advice is candidate guidance until the browser environment proves it.

The preferred learning pattern is:

```text
specialist guidance if needed
→ controlled EXP-N browser experiment
→ write observed recipe/procedure if successful
→ fresh OpenCode session
→ EXP-N-R2 clean replay
→ promote recipe to verified only if replay succeeds
```

The **observed → replay-verified** distinction is a factory/harness quality rule, not an Infor-defined validation level.

A replay stopped because one of its own required acceptance conditions cannot be satisfied is **blocked**, not evidence that the underlying procedure failed.

The harness/controller automates this coordination. Future coordinator replies must respect the harness action protocol and experiment boundaries supplied by the controller.

# 3. Decisions and rules established so far

Permanent factory knowledge must be evidence-based:

```text
candidate guidance
→ observed
→ replay-verified
```

A recipe is only verified after a clean replay in a fresh OpenCode conversation reproduces its required semantic postconditions.

Core rules:

-   Modify only factory-owned FX\_ artifacts.
-   Never alter unrelated/non-FX\_ artifacts.
-   Never weaken security or expose credentials.
-   Keep experiments narrowly scoped to one new capability.
-   Read current state before retrying; never blindly replay a mutation after interruption.
-   Record failures, blockers and corrections, not just successes.
-   Evidence should prove state transitions, not every click.
-   A runtime screenshot proves only that a visual state rendered at that moment.
-   An independent Designer reopen is a practical UI-level persistence test, not direct durable-storage proof.
-   A newly opened Designer tab is not automatically a complete cache boundary.
-   Explicitly distinguish editing permission from editing scope.
-   Identify the exact Form version by **Form name + ScopeType + ScopeName**.
-   Treat specialist/documentation guidance as candidate evidence for exact **2026.09.08** behavior until the browser environment proves it.
-   Do not generalize recipes beyond the environment, property/component types and workflow actually replayed.
-   Save semantics must be learned experimentally.
-   After editing Form metadata, compare the saved value with the same Form version after the experiment's required cache/reopen boundary.
-   Do not invent undocumented APIs, direct DB changes, or metadata hacks to force an experiment through.
-   In Select Form, explicitly select the intended row rather than assuming Enter will activate the filtered row.
-   If an experiment defines a prerequisite before an action, obey that prerequisite even when the underlying product would permit the action. A harness restriction is not a Mongoose product requirement.
-   EXP-005-R2 must remain recorded as a **blocked replay**; its explicit unload and final comparison never occurred.
-   Do not change Unload IDO Metadata With Forms merely to satisfy an experiment unless a separately approved scope permits that mutation.
-   Form/global-object cache and IDO metadata cache are distinct concepts, although a supported unload can clear both when the preference is enabled.
-   **Unload All Global Form Objects is a cache-invalidation operation, not a persistence operation.** The Caption must already have been saved. The unload tests retrieval after a stronger cache boundary; it does not commit the Caption.
-   Treat **Unload All Global Form Objects** as a **global/cache-wide side effect**, not an operation scoped only to the target Form. It can clear Forms/global objects from memory and, with the preference enabled, can also affect IDO metadata for the configuration.
-   EXP-006 confirms the documented coupled-unload path works as expected in this **2026.09.08** environment and proves its Caption postcondition once; it does not establish the general validity of that Mongoose operation, which product documentation already documents.
-   A single successful EXP-006 execution remains **observed**, not replay-verified.
-   Repeated Ext IDs, store indexes and internal component structures are diagnostic observations, not durable recipe dependencies.
-   If existing evidence already proves an acceptance check, reuse it rather than performing unnecessary browser actions or re-logins.

Current naming conventions:

```text
Forms:       FX_<Purpose>
Components:  FX_<SemanticPurpose><MongooseType>
Variables:   FX_<Purpose>Var   (candidate from EXP-004; no verified variable recipe)
```

# 5. Negative findings / blocked topics and why

**EXP-004 — Form Variable Fundamentals is blocked.**

Correct Form-variable UI:

```text
Web Designer
→ Details
→ Variables
```

Edit → Variable opens **Global Objects** and is not the Form-variable creation path.

FX\_TestValueVar could be created with:

```text
Global = False
Persistent = False
Value = Seed-A
```

Its definition then failed to survive:

-   ordinary Form Save: **2/2 failures**
-   Regenerate Form: **1/1 failure**
-   total: **3/3 failures**

No variable recipe exists.

This is anomalous relative to the documented model: Web Designer supports creating/modifying Form variables, including temporary variables, and Regenerate Form is documented with save/close/reopen semantics. This does not prove a product defect.

Possible causes remain:

-   2026.09.08 product defect,
-   configuration issue,
-   scope/version interaction,
-   unobserved prerequisite,
-   other environment-specific behavior.

Persistent=False controls persistence/lifetime of the variable's **value**. It does not imply that the Form-variable definition should disappear after the Form is saved.

Do not work around EXP-004 using bindings, scripts, undocumented APIs, DB edits, Global=True, Persistent=True, or manual metadata manipulation.

**EXP-005-R2 remains historically blocked by its own isolation criteria.**

EXP-006 does not retroactively convert it into a successful replay. EXP-006 was a separately approved experiment that deliberately permitted the documented coupled-cache side effect.
