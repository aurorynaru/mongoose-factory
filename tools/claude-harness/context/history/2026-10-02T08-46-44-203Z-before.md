# 1. Project and workflow

The project is an autonomous **Infor Mongoose factory** being built in C:\\AI\\mongoose-factory. Its long-term goal is to take a natural-language request, optionally with reference images, and reliably build Mongoose Forms/portal-related artifacts using browser automation and a growing set of verified recipes.

There are three roles:

-   **Coordinator (ChatGPT):** decides the next bounded experiment step, reviews worker evidence, decides whether specialist consultation is needed, and controls knowledge promotion from candidate → observed → replay-verified.
-   **OpenCode worker:** operates the actual Mongoose browser through Playwright MCP, writes/updates experiment records, recipes, and evidence files, and must follow the current experiment scope exactly.
-   **Infor Mongoose specialist GPT:** provides Mongoose-domain guidance when a genuinely new concept or unexplained product behavior appears. Its advice is candidate guidance until the browser environment proves it.

The preferred learning pattern is:

```text
specialist guidance if needed
→ controlled EXP-N browser experiment
→ write observed procedure if successful
→ fresh OpenCode session
→ EXP-N-R2 clean replay
→ promote procedure/recipe to verified only if replay succeeds
```

The **observed → replay-verified** distinction is a factory/harness quality rule, not an Infor-defined validation level.

A replay stopped because one of its own required acceptance conditions cannot be satisfied is **blocked**, not evidence that the underlying procedure failed.

“Fresh worker context” or “independent execution” means independent at the harness/OpenCode-session level. It does **not** imply replication in a different Mongoose environment, configuration, user class, tenant, or product version.

The harness/controller automates this coordination. Future coordinator replies must respect the harness action protocol and experiment boundaries supplied by the controller.

Current Infor documentation supports that closing a Form can leave the Form and associated global Form objects in memory. Therefore ordinary close/reopen is not necessarily a complete Form/global-object cache boundary.

Unload All Global Form Objects clears cached/in-memory Form and global-Form-object information. It does not save unsaved Form changes. Therefore the tested property change must already be saved before invoking the unload.

With Unload IDO Metadata With Forms enabled, IDO metadata can also be cleared in association with Form unloading. Form/global-object cache and IDO metadata cache remain distinct concepts.

There is a documentation ambiguity around the exact IDO-metadata trigger. Current Web Client Behavior documentation describes IDO metadata unloading **when Forms are closed**, while other current development/cache documentation describes the preference as coupling IDO-cache clearing to **Unload All Global Form Objects**. These statements may both be true. EXP-006/R2/007 deliberately did not isolate the triggers, so for exact **2026.09.08** behavior—ordinary close, explicit unload, or both—remains **unverified**.

“Global Form Objects” names a Mongoose object category and must **not** be interpreted as proof of tenant-wide, server-wide or all-user invalidation.

Current online product references used by the specialist are principally **2026.10/2026.x**, not an exact archived 2026.09.08 documentation set. Browser evidence remains authoritative for exact 2026.09.08 wording and observed behavior.

# 3. Decisions and rules established so far

Permanent factory knowledge must be evidence-based:

```text
candidate guidance
→ observed
→ replay-verified
```

A procedure is verified only after a clean replay in a fresh OpenCode conversation reproduces its required semantic postconditions. Passing every acceptance check in the first execution makes the result **observed**, not replay-verified.

Core rules:

-   Modify only factory-owned FX\_ artifacts.
-   Never alter unrelated/non-FX\_ artifacts.
-   Never weaken security or expose credentials.
-   Keep experiments narrowly scoped to one new capability.
-   Read current state before retrying; never blindly replay a mutation after interruption.
-   Record failures, blockers and corrections, not just successes.
-   Evidence should prove state transitions, not every click.
-   A runtime screenshot proves only that a visual state rendered at that moment.
-   An independent Designer reopen is a practical UI-level persistence test, not direct proof of a durable Forms-database row.
-   A newly opened Designer tab is not automatically a complete cache boundary.
-   Explicitly distinguish editing permission from editing scope.
-   Identify the exact customized Form version by **Form name + ScopeType + ScopeName**.
-   Never treat matching Form Name alone as proof that the intended scoped version reopened.
-   Treat specialist/documentation guidance as candidate evidence for exact 2026.09.08 behavior until browser evidence proves it.
-   Do not generalize beyond the environment, property/component types and workflow actually replayed.
-   Save semantics must be learned experimentally.
-   After editing Form metadata, compare the saved value with the same scoped Form version after the experiment's required cache/reopen boundary.
-   Do not invent undocumented APIs, direct DB changes, or metadata hacks.
-   In Select Form, explicitly select the intended row rather than assuming Enter activates the filtered row.
-   If an experiment defines a prerequisite, obey it even when the product itself might permit another path.
-   Do not change Unload IDO Metadata With Forms merely to satisfy an experiment unless separately approved.
-   Form/global-object cache and IDO metadata cache are distinct concepts, although the preference can couple IDO-cache clearing to Form unloading behavior.
-   **Unload All Global Form Objects is cache invalidation, not persistence.** The Form change must already have been saved; the unload tests subsequent retrieval.
-   Treat the unload as broad Form/global-object cache invalidation within the exercised session/context. Do not infer wider system scope without evidence.
-   EXP-005-R2 remains a historically blocked replay; later experiments do not retroactively change that result.
-   **EXP-006 + EXP-006-R2 replay-verify literal User-scope Caption persistence across the tested unload sequence.**
-   **EXP-007 establishes literal User-scope Description persistence across the previously replay-verified unload sequence as observed only.**
-   Do not promote a reusable Description recipe or replay\_verified Description claim until an independent clean replay reproduces the semantic postconditions on a new FX\_ Form.
-   That Description replay should reproduce the same User scope and tested cache boundary. A different user, tenant, configuration or product release would be a separate generalization experiment, not required merely for factory replay verification.
-   Caption and Description are independent metadata fields. Evidence for one does not prove the other.
-   **Do not infer general Form-metadata persistence from Caption/Description persistence.** Other Form attributes and subordinate objects—collections, variables, components, event handlers, bindings and related definitions—require their own evidence.
-   Caption/Description results do not verify localized/translatable Strings, Site/Group scope, other unload mechanisms, cache internals or other Mongoose versions.
-   Repeated Ext IDs, store indexes, model IDs, internal request paths and component structures are diagnostic observations, not durable recipe dependencies.
-   If existing evidence already proves an acceptance check, reuse it instead of performing redundant browser operations.
-   If Web Client list data and reopened Designer properties differ, record only the observed difference unless the list/projection contract is known; do not infer stale data, fallback logic, cache defects or persistence failure.
-   Repository/worktree audits should distinguish experiment-authored files from harness/runtime and Playwright-generated side effects.

Current naming conventions:

```text
Forms:       FX_<Purpose>
Components:  FX_<SemanticPurpose><MongooseType>
Variables:   FX_<Purpose>Var   (candidate from EXP-004; no verified variable recipe)
```

# 4. Lessons learned and pitfalls per experiment

**EXP-001 — Environment fingerprint**

Established browser architecture, User-scope behavior, version information, and basic Web Client / Web Designer navigation. Editing permission and editing scope are separate concepts.

**EXP-002 / EXP-002-R2 — Basic Form creation**

Verified recipes/forms/create-basic-form.md.

Reliable semantic path:

```text
Web Designer
→ New
→ New Form
→ Classic
→ BuildFromScratch
→ wizard
```

Pitfalls include wrong-row activation in Select Form, portal notifications intercepting clicks, drifting Ext IDs and unreliable synthetic DOM events.

This verified recipe was subsequently reused by later Form-property experiments.

# 5. Negative findings / blocked topics and why

**EXP-004 — Form Variable Fundamentals is blocked.**

Correct Form-variable UI:

```text
Web Designer
→ Details
→ Variables
```

Edit → Variable opens **Global Objects** and is not the Form-variable creation path.

FX\_TestValueVar could be created with:

```text
Global = False
Persistent = False
Value = Seed-A
```

Its definition then failed to survive:

-   ordinary Form Save: **2/2 failures**
-   Regenerate Form: **1/1 failure**
-   total: **3/3 failures**

No variable recipe exists.

This behavior is anomalous relative to documented Form-variable support, but root cause remains **unverified**: possible 2026.09.08 defect, configuration issue, scope/version interaction, unobserved prerequisite, or another environment-specific condition.

Persistent=False governs the lifetime/persistence of the **variable value** across Form executions; it does not explain why the variable definition itself disappeared and does not mean the variable is global.

Do not work around the blocker with bindings, scripts, undocumented APIs, DB edits, Global=True, Persistent=True, or manual metadata manipulation unless a separate experiment explicitly authorizes such work.

**EXP-005-R2 remains historically blocked by its own isolation criteria.** EXP-006/EXP-006-R2 do not retroactively make that replay successful.

The GetAllForms/list-versus-Designer Caption discrepancy remains an unresolved browser observation. It is not evidence, by itself, of stale data, persistence failure, cache defects or a known fallback/projection rule.

The exact 2026.09.08 IDO-metadata trigger remains unresolved. EXP-006/R2/007 combined ordinary close and explicit global-object unload while the preference was enabled, so they cannot establish which action caused any IDO-cache clearing.
