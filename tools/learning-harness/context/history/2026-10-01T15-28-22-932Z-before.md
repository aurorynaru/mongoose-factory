# 1\. Project and workflow

The project is an autonomous **Infor Mongoose factory** being built in C:\\AI\\mongoose-factory. Its long-term goal is to take a natural-language request, optionally with reference images, and reliably build Mongoose Forms/portal-related artifacts using browser automation and a growing set of verified recipes.

There are three roles:

-   **Coordinator (ChatGPT):** decides the next bounded experiment step, reviews worker evidence, decides whether specialist consultation is needed, and controls knowledge promotion from candidate → observed → verified.
-   **OpenCode worker:** operates the actual Mongoose browser through Playwright MCP, writes/updates experiment records, recipes, and evidence files, and must follow the current experiment scope exactly.
-   **Infor Mongoose specialist GPT:** provides Mongoose-domain guidance when a genuinely new concept or unexplained product behavior appears. Its advice is always treated as candidate guidance until the browser environment proves it.

The preferred learning pattern is:

```text
specialist guidance if needed
→ controlled EXP-N browser experiment
→ write observed recipe
→ fresh OpenCode session
→ EXP-N-R2 clean replay
→ promote recipe to verified only if replay succeeds
```

The harness/controller now automates this coordination. Future coordinator replies must respect the harness action protocol and experiment boundaries supplied by the controller.

# 3\. Decisions and rules established so far

Permanent factory knowledge must be evidence-based:

```text
candidate guidance
→ observed
→ replay-verified
```

A recipe is only verified after a clean replay in a fresh OpenCode conversation reproduces it without rediscovery.

Core rules:

-   Modify only factory-owned FX\_ artifacts.
-   Never alter unrelated/non-FX artifacts.
-   Never weaken security or expose credentials.
-   Keep experiments narrowly scoped to one new capability.
-   Read current state before retrying; never blindly replay a mutation after interruption.
-   Record failures and corrections, not just successes.
-   Evidence should prove state transitions, not every click.
-   A runtime screenshot proves that a particular visual state rendered at that moment (not bindings, data semantics, events, persistence or repeatability). An independent Designer reopen showing the metadata is the practical persistence test: it proves a fresh session can retrieve it, not direct storage proof.
-   Explicitly distinguish editing permission from editing scope.
-   Treat specialist/documentation guidance as candidate until the actual 2026.09.08 browser proves it.
-   Do not generalize a verified recipe beyond the environment/component types actually replayed.
-   Save semantics must be learned experimentally; immediate server events do not automatically mean an explicit Form Save is unnecessary.
-   Do not invent undocumented internal APIs, direct DB changes, or metadata hacks to make an experiment pass.

Current naming conventions established:

```text
Forms:       FX_<Purpose>
Components:  FX_<SemanticPurpose><MongooseType>
Variables:   FX_<Purpose>Var   (candidate from EXP-004 work; no verified variable recipe)
```

# 4\. Lessons learned and pitfalls per experiment

**EXP-001 — Environment fingerprint**

Established the browser architecture, User-scope behavior, version information, and basic Web Client / Web Designer navigation. Important lesson: permission and editing scope are separate concepts.

**EXP-002 / EXP-002-R2 — Basic Form creation**

Verified recipes/forms/create-basic-form.md.

Reliable path:

```text
Web Designer
→ New
→ New Form
→ Classic
→ BuildFromScratch
→ wizard
→ Save Template unchecked
→ Finish
```

Finish persisted the newly created blank Form immediately. The replay proved the procedure was durable across a fresh worker context.

Pitfalls discovered:

-   Select Form “OK” can activate the wrong row; native double-click on the exact row is safer.
-   Portal notifications can intercept clicks.
-   Generated Ext IDs drift.
-   Synthetic DOM events are unreliable on Ext controls.

**EXP-003 / EXP-003-R2 — Component Fundamentals**

Verified:

-   recipes/components/add-component-from-toolbox.md
-   recipes/components/configure-basic-component.md

Verified component types:

-   Static
-   Edit
-   Button

Deterministic observations across both runs included generated names static1\_USER, edit1\_USER, button1\_USER, item IDs lb0, ed1, bt2, default sizes, and newcomp type codes 0/1/8 — deterministic in EXP-003/R2 on 2026.09.08, **not** a supported selector/schema contract.

Important lessons:

-   Toolbox type → single-click canvas placement works.
-   Network observation (diagnostic only): property-grid edits sent GenerateServerEvent / updcompprop; placement sent newcomp. Recipes must rely on the semantic postcondition (component present with the requested type/name/properties after an independent reopen), not on these events.
-   Local compDef can remain stale until reload; do not use it as immediate authoritative proof after edits.
-   Explicit Save still finalizes the Designer session.
-   Static caption rendered with a trailing colon.
-   Button grid type can display PushButton while internal ctrl is button.

# 5\. Negative findings / blocked topics and why

**EXP-004 — Form Variable Fundamentals is blocked.**

The corrected Form-variable UI is:

```text
Web Designer
→ Details
→ Variables
```

Edit → Variable is the **Global Objects** editor and must not be used as the Form-variable creation path.

Within Details → Variables, FX\_TestValueVar could be created as a true Form-scoped variable with:

```text
Global = False
Persistent = False
Value = Seed-A
```

However, persistence failed.

Observed failure sequence:

-   Ordinary Form Save: variable disappeared after close/reopen, reproducible **2/2**.
-   Specialist found no documented variable-specific commit/finalization operation.
-   Specialist suggested one final documented alternate path: **Regenerate Form**.
-   Regenerate Form was tested once. It successfully issued the observed regenform close/reopen flow, but immediately after reopen the Form variable was gone again.
-   No global object was unintentionally created.
-   No recipe was written because the persistence postcondition failed.

Current classification (hypothesis, not established fact): **observed persistence failure inconsistent with documented Web Designer behavior** — current Infor documentation treats form variables as supported Designer objects and says Regenerate Form saves, closes and reopens the form. Likely a product defect or an environment/configuration-specific failure, pending Infor confirmation.

Important: **Persistent=False is about the runtime lifetime of the variable's value, not whether the variable definition is saved** in the form metadata. A temporary (non-persistent) form variable's definition should still survive a Designer reopen, so Persistent=False does not explain EXP-004.

Legacy / Windows Design Mode documentation describes Edit → Variable as a Variables dialog with both form and global variables. Current Web Designer is organised differently (Details → Variables vs. Global Objects). Do not re-apply legacy instructions to the current Web Designer.

Do not silently “fix” EXP-004 with:

-   bindings,
-   scripts,
-   undocumented APIs,
-   direct database edits,
-   Global=True,
-   Persistent=True,
-   manual metadata manipulation.

# 7\. Additional rules (from the Mongoose specialist's review, 2026-10-01)

1.  **Replay-verified ≠ documented/supported.** These are two independent axes. A technique can be documented + replay-verified, documented + currently failing, undocumented + reproducible, or undocumented + unstable. "Verified" in this factory means reproducible here, not Infor-supported.
2.  **Internal Web Designer traffic is diagnostic evidence, not a supported API.** Ext component IDs, GenerateServerEvent names (regenform, newcomp, updcompprop, …), payload keys, item IDs, numeric control codes, internal ctrl names and local JS structures (compDef, Ext stores) may be collected as evidence but must not become recipe dependencies or automation interfaces unless Infor documents them.
3.  **Recipes state semantic postconditions** (what is present after an independent reopen), not the protocol used to achieve them.
4.  **Scope/version awareness:** when an experiment changes or compares editing scope (User/Group/Site), close the form and refresh metadata before reopening; cached forms can otherwise show the previously loaded scope.
5.  **New forms vs. customizing existing forms:** both use the scope/version system, but upgrade/FormSync consequences differ. Factory experiments so far only create new FX\_ forms.
6.  The FX\_ naming scheme is a factory convention, not a Mongoose standard.
7.  Specialist answers that cite current (e.g. 2026.10) documentation are strong evidence but not proof of the exact 2026.09.08 behavior; the browser result decides.
