# 1. Project and workflow

The project is an autonomous **Infor Mongoose factory** being built in C:\\AI\\mongoose-factory. Its long-term goal is to take a natural-language request, optionally with reference images, and reliably build Mongoose Forms/portal-related artifacts using browser automation and a growing set of verified recipes.

There are three roles:

-   **Coordinator (ChatGPT):** decides the next bounded experiment step, reviews worker evidence, decides whether specialist consultation is needed, and controls knowledge promotion from candidate → observed → replay-verified.
-   **OpenCode worker:** operates the actual Mongoose browser through Playwright MCP, writes/updates experiment records, recipes, and evidence files, and must follow the current experiment scope exactly.
-   **Infor Mongoose specialist GPT:** provides Mongoose-domain guidance when a genuinely new concept or unexplained product behavior appears. Its advice is candidate guidance until the browser environment proves it.

The preferred learning pattern is:

```text
specialist guidance if needed
→ controlled EXP-N browser experiment
→ write observed recipe/procedure if successful
→ fresh OpenCode session
→ EXP-N-R2 clean replay
→ promote recipe to verified only if replay succeeds
```

The harness/controller now automates this coordination. Future coordinator replies must respect the harness action protocol and experiment boundaries supplied by the controller.

# 3. Decisions and rules established so far

Permanent factory knowledge must be evidence-based:

```text
candidate guidance
→ observed
→ replay-verified
```

A recipe is only verified after a clean replay in a fresh OpenCode conversation reproduces it without rediscovery.

Core rules:

-   Modify only factory-owned FX\_ artifacts.
-   Never alter unrelated/non-FX artifacts.
-   Never weaken security or expose credentials.
-   Keep experiments narrowly scoped to one new capability.
-   Read current state before retrying; never blindly replay a mutation after interruption.
-   Record failures and corrections, not just successes.
-   Evidence should prove state transitions, not every click.
-   A runtime screenshot proves that a visual state rendered at that moment, not bindings, data semantics, events, persistence or repeatability.
-   An independent Designer reopen showing the expected metadata is a **practical UI-level persistence test**, not direct durable-storage proof.
-   A newly opened Designer tab must not automatically be treated as a complete cache boundary; closed Forms/global objects may remain in memory.
-   Explicitly distinguish editing permission from editing scope.
-   Identify the exact Form version under test by **Form name + ScopeType + ScopeName**.
-   Treat specialist/documentation guidance as candidate until the actual 2026.09.08 browser proves the behavior.
-   Do not generalize a verified recipe beyond the environment, component/property types and workflow actually replayed.
-   Save semantics must be learned experimentally; immediate server events do not automatically mean explicit Form Save is unnecessary.
-   EXP-005 shows that ordinary Designer Save can persist at least a **literal Form-level Caption** edit in this environment. This does not establish identical save behavior for variables or other metadata classes.
-   After editing Form metadata, compare the saved value with the same exact Form version after a meaningful reopen/cache boundary.
-   Do not invent undocumented internal APIs, direct DB changes, or metadata hacks to make an experiment pass.
-   In Select Form dialogs, do not assume pressing Enter in a filter field opens the filtered row. EXP-005 observed Enter opening a previously selected row; explicitly select the intended row before invoking the open action.

Current naming conventions:

```text
Forms:       FX_<Purpose>
Components:  FX_<SemanticPurpose><MongooseType>
Variables:   FX_<Purpose>Var   (candidate from EXP-004; no verified variable recipe)
```

# 4. Lessons learned and pitfalls per experiment

**EXP-001 — Environment fingerprint**

Established browser architecture, User-scope behavior, version information, and basic Web Client / Web Designer navigation. Important lesson: permission and editing scope are separate concepts.

**EXP-002 / EXP-002-R2 — Basic Form creation**

Verified recipes/forms/create-basic-form.md.

Reliable path:

```text
Web Designer
→ New
→ New Form
→ Classic
→ BuildFromScratch
→ wizard
→ Save Template unchecked
→ Finish
```

Finish persisted the newly created blank Form immediately. The replay reproduced the procedure in a fresh worker context.

Pitfalls:

-   Select Form “OK” can activate the wrong row; native interaction with the exact intended row is safer.
-   Portal notifications can intercept clicks.
-   Generated Ext IDs drift.
-   Synthetic DOM events are unreliable on Ext controls.

**EXP-003 / EXP-003-R2 — Component Fundamentals**

Verified:

-   recipes/components/add-component-from-toolbox.md
-   recipes/components/configure-basic-component.md

Verified component types:

-   Static
-   Edit
-   Button

Deterministic observations across both runs included generated names static1\_USER, edit1\_USER, button1\_USER, item IDs lb0, ed1, bt2, default sizes, and newcomp type codes 0/1/8. These were deterministic in EXP-003/R2 on 2026.09.08 but are **not supported selector/schema contracts**.

Important lessons:

-   Toolbox type → single-click canvas placement works.
-   Internal traffic such as GenerateServerEvent, updcompprop and newcomp is diagnostic evidence only.
-   Recipes must depend on semantic postconditions after reopen, not internal event names.
-   Local compDef can remain stale until reload.
-   Explicit Save still finalizes the Designer session.
-   Static caption rendered with a trailing colon.
-   Button grid type can display PushButton while internal ctrl is button.

**EXP-005 — Form Caption Persistence**

Status: **COMPLETE — PERSISTED POSTCONDITION CONFIRMED. Procedure is observed, not replay-verified.**

FX\_FormPropertyLab01 was created as a User-scope classic BuildFromScratch Form using the verified creation recipe.

For this specific fresh Form in this environment, the Form-level Properties showed:

```text
Name        = FX_FormPropertyLab01
Description = empty
Caption     = empty
Version     = User version for the confirmed user
Device Type = Default
Form Type   = Normal
Is Master   = True
```

Do **not** generalize Caption = empty as the universal default for new Mongoose Forms. It is only the property-grid state observed for this specific BuildFromScratch Form; fallback/default behavior was not separately tested.

Only Caption was changed to the literal value:

```text
Form Property Lab
```

Ordinary Designer Save returned the Designer to a clean state. After closing the Designer and opening the same User-scope Form in a new Designer tab, Caption was again Form Property Lab; Name, Version, Device Type, Form Type and Is Master matched the saved state.

This is strong UI-level retrieval evidence that the postcondition persisted within EXP-005, but the reopen did **not** deliberately clear cached Forms/global objects, so it is not yet the strongest possible cache-independent persistence test.

Important observations:

-   Web Client displayed Form Property Lab as the Form tab title, consistent with Caption being distinct from Form name.
-   The long-lived Select Form dialog continued to show FX\_FormPropertyLab01 in its Caption column while runtime/reopened Designer showed Form Property Lab. This is an **observed inconsistent/stale-looking display; cause unverified**.
-   A new Designer opened from the Web Client Designer button auto-loaded the Web Client's current Form after scope confirmation. Observed once only.
-   Pressing Enter in Select Form filtering opened a previously selected row rather than the intended filtered target in this session.
-   EXP-005 tested a **literal Caption only**. It did not test creation/use of a translatable String object for production localization.
-   The Caption procedure needs a clean R2 before any reusable Form-property recipe is considered replay-verified.

# 5. Negative findings / blocked topics and why

**EXP-004 — Form Variable Fundamentals is blocked.**

Correct Form-variable UI:

```text
Web Designer
→ Details
→ Variables
```

Edit → Variable opens the **Global Objects** editor and is not the Form-variable creation path.

Within Details → Variables, FX\_TestValueVar could be created as a Form-scoped variable with:

```text
Global = False
Persistent = False
Value = Seed-A
```

Persistence failed.

Observed failure sequence:

-   Ordinary Form Save: variable disappeared after close/reopen, reproducible **2/2**.
-   No documented variable-specific finalization operation was identified.
-   Regenerate Form was then tested once and completed its native save/close/reopen behavior, but the variable disappeared again.
-   Total persistence failure: **3/3 across both documented native save paths**.
-   After reopen the variable was absent from the Form variable list and GetFormDesigner result; attempts 1–2 also confirmed no unintended Global Object.
-   No recipe was written because the persistence postcondition failed.

Current classification: **candidate product defect or environment/release-specific persistence issue; root cause undetermined pending Infor confirmation**.

The evidence establishes that the behavior conflicts with documented Form-variable capability, but it does not distinguish a product defect from configuration, release-specific behavior, an unrecorded prerequisite, or another environment-specific cause.

EXP-005 provides useful comparison evidence that ordinary Designer Save is not generally incapable of persisting all Form metadata, because a literal Form Caption survived its save/reopen test. It does not identify the cause of the variable failure.

Important: **Persistent=False controls the runtime persistence of the variable's value; it does not imply that the Form-variable definition itself should disappear from Form metadata.**

Legacy / Windows Design Mode guidance must not be substituted for current Web Designer navigation.

Do not silently “fix” EXP-004 with:

# 7. Additional rules (from the Mongoose specialist's review, 2026-10-01)

1.  **Replay-verified ≠ documented/supported.** These are independent axes. “Verified” in this factory means reproducible here, not automatically Infor-supported.
2.  **Internal Web Designer traffic is diagnostic evidence, not a supported API.** Ext IDs, event names such as regenform, newcomp, updcompprop, payload keys, item IDs, numeric control codes, internal ctrl names and local JS structures may be observed but must not become recipe dependencies unless documented by Infor.
3.  **Recipes state semantic postconditions**, not the internal protocol used to achieve them.
4.  **Scope/version awareness:** when evaluating another editing scope/version, identify the target by object/Form name + scope type + scope name. Close the Form and clear cached Forms/global objects using the documented unload mechanism before evaluating the other version. Clear IDO metadata separately only when IDO metadata freshness is relevant.
5.  **New Forms vs. customizing existing Forms:** both participate in the scope/version system, but upgrade/FormSync consequences differ. User/Group/Site customizations are not equivalent to Vendor versions. Factory experiments so far create new FX\_ Forms.
6.  The FX\_ naming scheme is a factory convention, not a Mongoose standard.
7.  Specialist answers based on newer documentation are strong candidate evidence but not proof of exact 2026.09.08 browser behavior; experiment evidence decides what is reproducible here.
8.  **Successful persistence within one experiment is not replay verification.** EXP-005 confirmed its persisted postcondition, but the procedure requires a fresh-context replay before promotion.
9.  **A new Designer tab is not automatically a cache-independent session.** Closing a Form can leave Form/global-object definitions in memory; persistence replays should deliberately cross an appropriate documented cache/session boundary.
10.  **Literal Caption persistence and localized Caption design are separate capabilities.** EXP-005 covers only a literal Caption. Do not treat it as verification of translatable String-object creation or localization behavior.
